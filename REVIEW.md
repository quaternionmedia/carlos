# Pre-publication review

Date: 2026-08-18. Branch `adopt/qm-governance`, **nothing pushed**.

This file is for the human pass before publication. It is not a status
document — `GOVERNANCE.md` is that, and it is where the open conflicts live. It
is a list of what a reviewer should look at, what only a person can decide, and
what is deliberately not done.

Delete it once the review has happened. A review checklist that outlives its
review is a document that reads as current and is not.

## Run it yourself first

```bash
uv sync
uv run playwright install chromium   # once per clone
uv run carlos check                  # the suite and the walkthrough
uv run carlos harness                # the four frontend harnesses
uv run carlos gates                  # the governance gates
uv run carlos status                 # what state this checkout is in
```

`carlos --help` lists every durable round, and `carlos --dry-run <round>`
prints the command it runs — each is one you could type yourself.

failures named below and no others.

`GOVERNANCE.md` has the publishing procedure — what a publisher does, in order,
and which steps are remote writes.

## What only a person can decide

**1. Do the drawings look like the gear?** This is the one thing no assertion
settles, and it is the largest single piece of unreviewed work.

Five screenshots in `walkthrough/media/`, regenerated by the browser page. Every
*countable* claim about them is asserted — 88 keys as 52 naturals and 36 sharps,
64 pads on the Launchpad, 25 movable faders on the desk, a square Launchpad
panel, an empty console — and none of that says whether the shapes read as the
devices they stand for.

| Look at | And judge |
| --- | --- |
| `05-in-the-browser-keybed-and-desk.png` | Does the 88-note keybed read as a keyboard? Do the Qu-24's channel faders read as a desk? Are the Nord's striped drawbars visibly a different control from the desk's plain fader caps? |
| `05-in-the-browser-irl-drum-rig.png` | The Launchpad's 8×8 grid, the Hapax, two drum modules. **Relative sizing:** the drum module hits a 150px floor, so it draws 1.8× narrower than the Launchpad where reality is 6×. Too generous a floor? |
| | **Aspect compression:** the Hapax draws at 1.30 against a true 1.56, the drum at 0.50 against 0.31. Too aggressive? |
| `05-in-the-browser-boot.png` | The palette at its default corner, the status line, minimal mode — and the house navy behind all of it |
| the bar, at `/` | The bare port is the workspace now. Does the bar say enough, where the splash used to? |
| `05-in-the-browser-menu.png` | The eight-wedge ring |
| `05-in-the-browser-turned.png` | Cables after `Tab` — all four occluded with four anchors, which is correct for where those sockets are |

Also worth a hand rather than an eye: press a pad on the drawn Launchpad and
watch the bound drum voice light. The chain is asserted end to end, but whether
the 160ms flash is *readable* at pad size is a judgement.

**2. The licensing class.** `reuse-lint` fails and will keep failing until this
is settled: the outbound-licensing record puts services at AGPL-3.0-or-later and
the declared licence is MIT. **Publishing with it red is the decision**, taken
deliberately — settling a licence class to turn a check green decides the wrong
question for the wrong reason. It is still yours to settle.

Three files carry copyright information and the rest do not; `python -m reuse
lint` gives the current total, which moves with every file added. The class
question comes first, then `LICENSES/` and a header per file. This is the
largest remaining task in the repository and it is a decision, not typing.

**3. Whether the branch should be split.** It carries two bodies of work — the
governance adoption, and everything the application gained since. A publisher
may reasonably want them apart. They are on one branch because the async
contract allows one open pull request per contributor, so two branches would be
two pull requests that cannot both be open.

## What is deliberately not done

- **Instance discovery.** `/healthz` names the instance, its start time, the
  port actually bound and the resolved database path, so a measurement can be
  attributed. What is declined is the monitoring-seam record's *mechanism* —
  bind port 0, write a run-file — because it costs the predictable address that
  makes this a thing you open in a browser. A collector must be told where to
  look. Recorded in `GOVERNANCE.md` with the reasoning.
- **Outbound calls are planned and never sent.** `docs/interop.md` says why.
- **Named patch persistence.** Blocked on the datastore conflict.
- **The adoption record is unratified.** It is written and Proposed at
  `governance/qm/adr/DRAFT-adopt-the-qm-constitution.md`, carrying the component
  audit, the seam protocol, the service inventory, the risk register and twelve
  named conflicts. Ratifying it — status, number, index — is a human commit.
- **`walkthrough/` decision 7 is unmet.** A page that ran somewhere nobody
  merges has not run; the evidence has to be a job run on the default branch.
  `.github/workflows/tests.yml` exists to produce that evidence and cannot
  until something is pushed. **A file that would have run is not a run.**

## What the tests will not catch

Stated because an unstated boundary reads as coverage.

- **Real MIDI hardware.** Everything else about MIDI runs through a synthetic
  source down the same path a real port uses; a real port needs a real device.
- **Prose.** The walkthrough's *examples* cannot drift, because they execute.
  The sentences around them are ordinary prose and age like it — roughly four
  lines in ten of a page are checked.
- **How it looks.** See item 1. The screenshots are recorded, never compared: a
  test that diffs images fails on a font and gets switched off, taking the
  assertions beside it.
- **A remote run.** The workflow runner cannot reproduce `uses:` steps, the
  runner image, or secrets. A local pass is not a remote pass.
